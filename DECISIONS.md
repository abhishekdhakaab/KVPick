## 2026-10-16

**D1. [ACTIVE] Model variant: `Qwen/Qwen3-4B-Instruct-2507` (not `Qwen/Qwen3-4B`).**
Same architecture and KV shape (36 layers, 8 KV heads, head_dim 128, bf16, Apache-2.0, 8.06 GB).
Reason: `Qwen3-4B` defaults to "thinking" mode and emits long reasoning before an answer, which makes the 100-question GSM8K generation eval slow and makes answer extraction fragile. The 2507 Instruct release is non-thinking only, so GSM8K generation is short and deterministic. Perplexity deltas are relative, so the instruct tuning does not affect the R4 verdict.

**D2. [ACTIVE] Long-context set: LongBench `qasper` for the quality test split, LongBench `hotpotqa` for the 8192-token calibration prompts.**
Reason: `THUDM/LongBench` ships as a dataset *script*, which `datasets>=4` refuses to load. Workaround: download `data.zip` from the hub and read the JSONL directly (recorded as a workaround for C1). Qasper contexts (median ~23k chars, roughly 6k tokens) fit in an 8192 window with the question; HotpotQA contexts (median ~62k chars) are long enough to truncate to exactly 8192 tokens for G1. Using different subsets keeps calibration and test disjoint by construction.

**D3. [ACTIVE] Calibration vs test split.** Calibration (G1 stats, G2 axis choice): 20 WikiText-2 windows + 5 HotpotQA prompts. Test (G3 quality): 50 *different* WikiText-2 windows, 100 GSM8K test questions, 50 Qasper examples. Window ids are stored in manifests so disjointness is checkable.

**D4. [ACTIVE] The reference landscape moved since the plan was written; the plan is updated, not the thresholds.**
- KVServe now requires `vllm>=0.18.0` and `torch>=2.10` (plan said vLLM 0.10.1). Latest vLLM on PyPI today is 0.31.0 (2026-10-05).
- KVServe has shipped **its own fused kernels** (TileLang Hadamard+quant, and a CUDA runtime `kvs_compress.cu` with per-channel / per-token quantize kernels). So "fast fused kernels for KIVI-style quantization" already exist in open source. This weakens the novelty of our kernel piece but does not change R5: R5 asks whether there is headroom over PyTorch/torch.compile at all. Noted for the recommendation section.
- KVServe's quantizer writes **one uint8 per value** (levels 12 or 16, i.e. about 4 bits of information) and relies on an nvCOMP/LC entropy codec to get the byte reduction. Our bit-packed INT4/INT8 gets the reduction directly without a codec stage. The two are therefore not the same operation; a G4 comparison against KVServe must be "quantize + codec" vs "bit-packed quantize", and this will be stated.

**D5. [ACTIVE] Attention-output error metric (G2) uses queries sampled from the captured K rows of the same layer/head, plus Gaussian queries scaled to the K row RMS as a second column.** Reason: we do not capture Q. Post-RoPE keys live in the same rotated space as queries, so key rows give realistic logit magnitudes; pure Gaussian queries give near-uniform softmax and would understate the error.

**D6. [ACTIVE] Quantization scheme in the reference is asymmetric min/max with a zero point (KIVI and KVServe both do this), scales and zero points stored as fp16.** The spec's symmetric amax scheme is kept as a flag (`--symmetric`) for continuity but is not the default, because asymmetric is never worse at the same bit width and is what the literature compares against. Byte accounting includes 2 bytes scale + 2 bytes zero per group.

**D7. [COMPLETED] Free preview on Qwen3-0.6B before renting a GPU.** Qwen3-0.6B (28 layers, same 8 KV heads x 128 head_dim, same q/k RMSNorm design) was captured on the laptop CPU for 5 WikiText-2 calibration windows and 1 HotpotQA 8192-token prompt, and G1/G2 were run on it. Results (results/G1_kv_stats.json, results/G2_axes.json as of 2026-10-16, to be overwritten by the 4B run): key top-1%/median channel ratio 58.8x at layer 0 and >= 5x in 27 of 28 layers; per-channel 4-bit keys reduce attention-output error by 61% vs per-row and 32% vs per-row-g32. These are **previews**; R2/R3 verdicts are only taken from the 4B run. Reason for doing it: R2 and R3 drive the kernel design, and a 0.6B preview costs nothing.

**D8. [ACTIVE] Checker memory probe runs first.** (After D10 this concerns the internal test harness only.) On CPU the hidden-buffer mutant escaped detection because its temporary had already been allocated and freed by earlier checks and the allocator reused resident pages. The memory check is now the candidate's first call. On GPU, `torch.cuda.max_memory_allocated` is reset per check and does not have this problem. Thresholds unchanged.

**D9. [ACTIVE] Bytes-per-token convention.** All compression ratios use fp16 scale + fp16 zero per group (asymmetric). The spec's table (fp32 scale, symmetric) gives 1.939x for INT8 and 3.2x for INT4-g32; ours give 1.94x (int8_row) and 3.20x (int4_row_g32 and int4_kivi) by coincidence of 2x2 B meta vs 1x4 B. int4_row (one group per 128) reaches 3.76x but G2 shows it is the worst for accuracy.

**D10. [ACTIVE, CHANGES plan section 0.3 item 2 and rule R10 weight] The mutation-tested "checker" is demoted from project deliverable to internal test suite (2026-10-16).**
Count of kernels this project writes: ~12 variants (2 formats x 2 directions x 3 versions), all our own. A verification harness only earns a headline when other people's or machine-written kernels flow through it, which is a different project. The tests (bit-exact reference match, real-outlier inputs, sentinel/anti-skip, memory, stream safety) are kept and used as CI for our kernels; the six mutants and the "checker" framing are dropped from the report's recommendation. R10 is recorded but no longer weighs on the go/no-go. The project becomes two pieces: verified fast kernels measured against the bandwidth ceiling, and the measured send-vs-recompute planner validated on a two-GPU harness.

**D18. [ACTIVE] R7 reading and a benchmark bug.** First G6 run had a test bug: every pipelined chunk copied the whole buffer, so pipelined goodput read ~2.5 Gbps at every rate. Fixed (each chunk copies its own slice) and rerun on the pod. Final G6: single-shot goodput exact (<= 1% error) at all points up to 25 Gbps and at 100 Gbps for 10 MB; at 100 Gbps with 100 MB and 1 GB the real single-GPU host-staged copy (about 9-10 GB/s) is slower than the emulated link, so the transfer is copy-bound (-1% and -21%). Pipelined 36-chunk transfers add a per-chunk sync cost that dominates for 0.3 MB chunks above 10 Gbps. R7 as pre-registered ("within 5% at every tested point") therefore **FAILS**, but the cause is the physical copy path at 100 Gbps on one GPU, not emulator timing. Consequence for any build: the emulator is trustworthy for links up to 25 Gbps on this harness; 100 Gbps needs a real peer-to-peer two-GPU path (G7, not rented) and larger chunks.

**D21. [ACTIVE] Reference quantizer epsilon changed from 1e-8 to 2^-24.** The reference clamps the scale with `clamp_min(EPS)` *before* rounding to fp16; fp16(1e-8) is 0, so an all-constant group produced scale 0, (x-zero)/0 = NaN codes, and only the dequantize (NaN*0+zero... in practice garbage*0+zero) hid it. 2^-24 is the smallest fp16 subnormal, survives the rounding, and makes every code finite and well defined. Effect on measured numbers: none (no real KV group has range < 15*2^-24). The feasibility results are not rerun; the CUDA kernel is bit-exact against the fixed reference.

**D24. [ACTIVE] Quantization step redefined as multiply-by-reciprocal: code = rint((x - zero) * (1/scale)) with the reciprocal computed once per group.** Previously code = rint((x - zero)/scale). On the A5000 the compression kernels were instruction-bound (K 54%, V 66% of the copy ceiling while the identical-byte dequantize kernels sit at 100%); an IEEE fp32 division per element costs ~10-15 instructions, a multiply costs 1. The Python reference, the C++ CPU reference and the CUDA kernels all change together, so bit-exactness is preserved (`1.0/scale` in torch is IEEE division; `__frcp_rn` is the correctly rounded reciprocal; both multiplies round once). Numerical effect: at most one-code differences at exact rounding boundaries; the quality eval is rerun with the final kernel in the next A40 session anyway. The spec explicitly allows defining the reference to match the hardware-friendly operation.

**D25. [ACTIVE] Kernel outcome on the RTX A5000 debug pod (development numbers, never reported as results).**
- v0 naive: ~30% of the device-copy ceiling. v1 (K: 256-thread tile per 32 tokens x 4 heads, 32 tokens held in registers; V: warp per row, 8-lane shuffles): after D24, K 102% and V 101% of the ceiling at T=8192, i.e. memory-bound at the roofline. Before D24 the same kernels were 54% / 66%: the per-element IEEE division made them instruction-bound. Lesson recorded for the write-up: on this op the compiler and the hand kernel were both compute-limited by one division, not by memory.
- v2 fused (one launch for all K tiles and V rows of the layer batch): first version 70% because the fused kernel inherited the K path's 94 registers and starved the V blocks of occupancy (V alone needs 22). Two fixes: V path rewritten to two rows per warp with 16-byte loads (more bytes in flight per warp), and `__launch_bounds__(256, 3)` capping the fused kernel at 80 registers with no local-memory spills. Result: 96% at T=128, 100% at T=512, 101% at T=2048 and T=8192. v2 dominates v1 at every size and is the shipped kernel; v1 remains as the measured intermediate step.
- torch.compile (max-autotune-no-cudagraphs) on the same op: 48-49% of the ceiling at every size on this card. Dequantize: v1 at 100% of ceiling for both K and V; the compiler reaches 83-87%.
- compute-sanitizer memcheck, racecheck, synccheck, initcheck: 0 errors on T in {1, 40, 97} with H in {6, 8}, all versions. 58 GPU tests + 80 CPU tests pass; the CUDA kernels, the C++ CPU reference and the Python reference are bit-identical.
- Nsight Compute counters are blocked on RunPod (ERR_NVGPUCTRPERM), as the spec anticipated; the device-copy ceiling is the roofline proxy. The standalone C++ benchmark (`bench_main.cu`) is dropped: CUDA-event timing around a single kernel launch already excludes Python overhead, and a torch-free launcher split is not worth the time.
- Pod: 1x RTX A5000 on-demand, roughly 55 minutes including all debugging, well under $0.30.

**D26. [ACTIVE] Planner and cost-model design.**
- Cost tables live in `results/cost_tables_a40.json`, generated by `scripts/build_cost_tables.py` from the feasibility JSONs with a provenance string per entry. Prefill model `ms = c0 + c1 n + c2 n^2 + c3 n m` fitted by relative least squares on 14 measured (n_new, m_cached) points: max error 13.7%, mean 8.0% (the first attempt, absolute least squares with one shared attention term, had 68% / 27% and was rejected). Decode step `ms = d0 + d1 batch` from 3 points.
- Kernel times for `int4_kivi` and `int8_row` are torch.compile placeholders from feasibility G4/G4b until the A40 results session measures our kernel; flagged in the JSON and irrelevant below ~100 Gbps (ms vs hundreds of ms).
- Quality classes from feasibility G3 under `configs/quality_budgets.yaml` (limits written before classification): raw strict, int8_row strict, int4_kivi normal (GSM8K -2.0 pts, Qasper -1.9 pts, ppl +0.05%), int4_row_g32 lenient, int4_row none.
- Planner (`kvpick/planner/planner.py`) is a pure function of (request, link, decode load, cost model): candidates = sends whose class meets the budget + recompute; recompute is infeasible when the decode GPU has running sequences and the prefill stall exceeds the request's ITL SLO; pick the minimum estimated KV-ready time; ties within 1% go to the higher-quality action (raw, recompute, int8, kv4); a stale link estimate falls back to recompute if harmless, else the highest-quality send. Transfer is modelled serially (compress + wire + decompress); pipelining could hide at most the kernel time and is not claimed.
- Evaluation is a cost-model evaluation (decision map + synthetic multi-round workload), not a queueing simulation (D20). Every figure says so.

**D27. [ACTIVE] Planner result and how it is framed.** On the measured A40 cost model: with the decode GPU idle and a normal budget, recompute is the fastest action only below 1.2-3.6 Gbps (lower when a long prefix is already cached: at 8192 cached tokens and 128 new tokens, KV4 send wins even at 1 Gbps); KV4 send wins everywhere else up to 100 Gbps; INT8 appears only for strict-budget requests; RAW never wins. On the synthetic multi-round workload the planner beats the best fixed policy ("always KV4, INT8 when the budget forbids KV4") by 5.2% mean KV-ready time at 1 Gbps, 1.2% at 2 Gbps and 0% from 3 Gbps up. This is reported as is: the deliverable is the measured decision map and crossover speeds, not a large planner speed-up, and the write-up says that the simple rule "KV4 unless strict, never raw, recompute only below ~3 Gbps on an idle decode GPU" captures the planner. Both figures are labelled "cost-model evaluation, not a queueing simulation".

**D29. [ACTIVE] Scale arithmetic made explicit: scale = fp16_rn(max(range * fp32(1/15), 2^-24)), a multiply, in the Python reference, the C++ reference and the kernels.** Found on the A40 with real KV: 1 in ~50,000 groups had a scale one fp16 ulp apart between kernel and reference (and 4 payload bytes in 56 M). Cause: PyTorch implements `tensor / python_scalar` as a multiply by the reciprocal, while the kernel divided by 15; the two round differently in rare cases. Random-data tests never hit it; real KV did. The reference now states the multiply explicitly so no implementation detail of torch is being relied on. Numerical effect nil in practice (one ulp of a scale in rare groups); all bit-exactness tests and the quality run's in-loop assertion are the check.

**D30. [ACTIVE] Cross-GPU transfer in the harness goes GPU0 -> pinned host -> GPU1, not peer-to-peer.** Measured on the 2x A40 node (topology SYS: different sockets, no NVLink): the direct peer copy costs a fixed ~49-99 ms per call regardless of size (1 MB: 49 ms; 10 and 100 MB: 98.5 ms; 1 GB: 148 ms), so the first transfer run floored at ~99 ms per copy and the pipelined mode at 36 x that. Pinned-host staging measured 20 GB/s (160 Gbps) with no fixed cost, well above every emulated link in the grid (<= 25 Gbps), so the link emulator remains the bottleneck by design. **D36. [COMPLETED, re-opens D17] A real kernel-level benchmark against KVServe's CUDA kernels and KIVI's pack step was missing from the project; adding it now that a RunPod GPU is available for the run.** D17 marked KVServe NOT_RUN because installing vLLM >= 0.18 + nvCOMP for the full connector was judged not worth 10-20 minutes of install risk when G4 already answered "is a fused kernel faster than PyTorch" against torch.compile. That reasoning does not cover the question now being asked: is KVPick's kernel faster than KVServe's *own* fused kernel and KIVI's pack step, at the same bit depth, on the same tensors. Re-reading both clones (`feasibility/external/kvserve`, `feasibility/external/kivi`, both already present from the C2 review) found a cleaner path than D17 anticipated:

- `kvserve_v1/compression/runtime/*` (layout, pipeline, manager, spec, cpp_backend, config) is vLLM-free by its own docstring ("No vLLM import or implicit network operation occurs") and only `kvserve_v1/compression/manager.py` (a *different*, higher-level file used by the request-level `KVCompressionAdapter`) imports `vllm.logger`. Avoiding that one file avoids the vLLM dependency entirely.
- The two quantize kernels that matter (`quantize_channel_kernel`, `quantize_token_kernel` in `compression/runtime/csrc/kvs_compress.cu`) are plain functions taking raw pointers + ints; the surrounding 736-line file's complexity (flat int64 metadata blob, paged-attention block strides, ANS codec workspace) is needed only by the full serving-time pipeline, not to call the kernels once on a `[T, H, D]` tensor.
- Decision: vendor those two kernels (plus `dequantize_channel_kernel`/`dequantize_token_kernel`, and their small device helpers) verbatim into `csrc/baselines/kvserve_kernels.cu`, under Apache-2.0 attribution in the file header, with fresh host launchers (not vendored) written for this benchmark. This is lighter than driving their real `CompressionRuntime` (which would require constructing paged-attention-shaped slots, arenas and block indices this project has no other use for) and keeps the kernel bodies byte-for-byte theirs, which is the whole point of a comparison.
- KVServe's quantize kernels are **coarser-grained** than ours and must be reported as such, not normalised away: `quantize_channel_kernel` takes one (min, scale) per (head, dim) over the *whole* T axis handed to it (no 32-token grouping); `quantize_token_kernel` takes one (min, scale) per token over *all* heads and dims (no 32-dim grouping). Both write one uint8 per value (no bit-packing); KVServe's real byte reduction comes from a separate nvCOMP/LC codec stage that this benchmark does not run (confirmed already in D4/C2_kvserve.md). `levels=16` is passed so the code range (0..15) matches our 4-bit codes, for a same-bit-depth *kernel speed* comparison; it is not a same-accuracy comparison.
- KIVI (`feasibility/external/kivi/quant/new_pack.py`, MIT) is imported directly, unmodified, from the existing clone: `quant_and_pack_kcache`/`quant_and_pack_vcache` use the *same* grouping as KVPick (K: per-channel per-32-token-group; V: per-token per-32-dim-group) and pack to the same 0.5 B/value density (8 x 4-bit codes per int32, vs our 2 codes/byte) -- the best-matched granularity of the three, but it is plain PyTorch with no custom CUDA kernel (confirmed in C2_kivi.md: KIVI's only CUDA code is a fused dequant+GEMV for decode attention, not reusable here), so it is a "no kernel was written" baseline rather than a kernel-vs-kernel one.
- Driver: `scripts/bench_baselines.py`, same `Timer`/CUDA-event/L2-flush convention as `scripts/bench_kernels.py`. Reports per-(K, V, T) median/p95 latency, ns/token (the one number comparable across all three regardless of output format), and GB/s against input-only and input+output bytes. Needs `triton` installed on the pod (KIVI's module imports it at module load even though this benchmark only exercises the plain-PyTorch pack path by default); everything else needs only `torch` + a CUDA toolchain already required for the project's own kernel.
- Status: code written and reviewed on the Mac (no GPU here to execute or verify the CUDA compiles); not yet run. Pending the GPU session: confirm the vendored kernels build and are bit-sane (spot-check a dequant round trip against the quantize output), then produce `results/baselines_<gpu>.json` and fold this comparison into the README's "what is and is not new" section. If the vendored kernels fail to build or launch-check on the pod, fall back to timing KVServe's plain-PyTorch `quantizer_func.py` only, and say so, rather than spending the session debugging someone else's CUDA.

**D36 outcome (1x A40, run completed the same session, `results/baselines_a40.json`).** The vendored KVServe kernels built and launch-checked clean on the first attempt (no debugging needed); a dequant round trip against the quantize output on random input gave max abs error 0.24-0.29, consistent with a 4-bit (16-level) step over a ~[-3,3] bf16 range, i.e. sane, not garbage. KIVI's pack functions ran unmodified (two PyTorch deprecation warnings about non-tuple advanced indexing, no functional issue). All three produced the same token counts in and no NaNs.

| | T=512 K / V (us) | T=2048 K / V | T=8192 K / V |
|---|---|---|---|
| KVPick v2 (ours) | 10.2 / 7.6 | 18.0 / 15.1 | 48.5 / 43.4 |
| KVServe CUDA kernel | 11.5 / 8.9 | 30.0 / 18.1 | 121.8 / 59.5 |
| KIVI pack (PyTorch) | 24279 / 5864 | 98844 / 5985 | 392947 / 5902 |

KVPick's kernel is faster than KVServe's at every size, by a widening margin on K (1.1x at T=512 -> 2.5x at T=8192) and a roughly flat margin on V (1.2x -> 1.4x). The K-side gap grows because KVServe's `quantize_channel_kernel` holds a fixed 8-channel block loop serially over the whole T axis with 32 token-lanes of parallelism regardless of T, while KVPick's K kernel assigns one block per 32-token group, so block count (parallelism) grows with T; this is a real architectural difference, not a tuning gap, and is worth a line in the kernel section of the README. KIVI's pack step is 500-8000x slower, which is the expected outcome of a Python-loop-based packer (`pack_tensor`'s 8-iteration advanced-indexing loop) with no custom kernel, not a meaningful kernel-speed finding -- it confirms C2_kivi.md's read that KIVI ships no quantize kernel to compare against, only a fused dequant+GEMV for decode. Its Triton-accelerated path is excluded as documented in `kvpick/baselines/kivi.py` (wrong axis for this comparison, not wired in).

Caveat carried over from the module docstring and worth repeating here: KVServe's kernel is quantizing to a *coarser* granularity (per-channel over the whole sequence; per-token over all heads/dims) than KVPick's grouped scheme, so this is a kernel-speed result at matched bit depth, not a matched-accuracy one -- KVServe would need its 32-token/32-dim grouping added (it does not ship one) to be an apples-to-apples accuracy comparison too.
